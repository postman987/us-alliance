# Jobs API

## 실행 방법

- 실행

```
yarn run start
```

- seed 데이터 생성(1000건)

```
yarn run seed
```

- 테스트

```
yarn run test
```

- 동시성 부하 테스트(목록 조회, POST를 무작위로 선택하여 동시에 100건 요청)

```
yarn run load-test
```

## 제약 사항

### 서버

- 단일 인스턴스, 단일 프로세스 상의 node.js 서버를 운용한다고 가정
- 해당 인스턴스에서 jobs.json 파일을 관리

### 데이터

- 최대 10만건의 job 데이터를 저장하여 관리하는 것으로 가정
- node-json-db를 기반으로 파일을 통해 데이터를 관리하고, node-json-db 특성상 각 요청에 대해 파일의 모든 데이터를 가져와 처리하기 때문에 성능을 고려하여 해당 수치를 가정
- 또한 작업 도메인이라는 휘발성이 있는 데이터 특성상 1주일의 보존 기간을 고려함

## 결정 사항

### 데이터 설계

- id는 유일한 uuid로 관리
  - api 요구사항으로 id를 통한 job 데이터 조작이 가능해야 하므로, 유일성을 보장할 수 있는 데이터 사용
- job의 id를 key로 사용하여 job 데이터를 관리
  - 특정 key를 기준으로 데이터를 조작하는 api 요구사항이 있어 key를 통한 search 방식이 효율적인 측면이 있음

### 동시성 제어

- 상호배재와 대기큐를 적용하여 동시 요청을 제어
- 하나의 요청 혹은 스케줄링 작업간 데이터 조회 후 처리하는 로직이 필요하여 각 요청마다 파일을 점유하도록 하고, 나머지 요청은 대기큐에 삽입되도록 함
- 이전 작업이 완료되면서 큐에 있는 데이터를 호출하여 연쇄적으로 요청이 처리되도록 구현

### 스케줄러

- 스케줄링 간격은 처리해야 하는 데이터의 양과 성능을 고려하여 1분으로, 한번에 처리하는 양은 20개로 결정
- 스케줄러가 파일을 점유하는 시간이 너무 길지 않아야 하며, 1주일의 보존 기간과 10만 건의 데이터를 고려하여 1분 간격과 20개로 결정

### 철회한 결정

- completed jobs
  - 완료된 jobs를 completed jobs라는 다른 파일로 관리하는 아이디어
  - node-json-db 특성상 모든 전체 파일을 한번에 조작하기 때문에 기본적으로 조작하는 데이터 양을 줄여 성능을 높이기 위한 결정
  - 다만 데이터를 옮기는데 파일을 여러번 조작해야 하며, 조회시 2개의 파일을 search해야 하므로 폐기
- node-json-db 내부적으로 데이터 접근시 mutex + queue를 적용한 동시성 제어가 적용되고 있어 이를 활용하고자 하였으나, 비즈니스 로직상 조회 후 데이터를 조작하는 케이스가 있어 추가적인 동시성 제어를 위한 mutex 추가
